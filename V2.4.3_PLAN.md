# Balance v2.4.3 — bugfixes

Status: SHIPPED 2026-08-16 — tag `v2.4.3`, all five items built in one pass, tested in demo (logic checks + visual).

## Bug 1 — weight chart: axis bounds read as data values

**Symptom** — chart showed 107.5 and 94.5, never entered; right label (105.9) didn't match the entered 105.8. Data verified correct — display problem only.

**Cause** — 107.5/94.5 are auto-scale bounds (data min/max ± 15% padding) with no visual distinction from data; 105.9 is the EMA trend endpoint label.

**Fix — LOCKED 2026-08-16**

- Remove both axis-bound labels.
- Right side carries exactly two numbers: current weight (latest real entry) and goal.
- Trend line unlabeled.
  *Intent: numbers appear only for values that exist (entries, goals). The line conveys direction and rate visually — never attach a number to a derived value on this chart.*
- One dot per entry (unchanged). Tap a dot → small chip "14 Aug · 106.0"; tap anywhere else dismisses.
- Inset ruler behind the data: faint hairlines at clean kg intervals, small values on sparse lines, drawn inside the plot area — chart size and layout unchanged.
- Label collision (weight approaching goal): weight label wins, goal label hides.
- Remove the old hover-only tooltips on dots and bars — chips replace them.

## 2 — 14-day calorie bars: tappable totals

**Change — LOCKED 2026-08-16**

- Tap a bar → chip "14 Aug · 1,850"; tap anywhere else dismisses.
- Chip is the same component and behavior as the weight-dot chip (Bug 1) — one shared implementation, not a copy.
  *Intent: identical tap-for-value interaction on both Trends charts.*

## 3 — Today: weight field rest/active states

**Change — LOCKED 2026-08-16**

- Rest state: field shows the last saved weight, greyed out — regardless of how long ago it was saved. Save button inactive.
- Typing anything activates Save. No same-value detection — re-saving an identical value is harmless.
- On save: value stores to the open day (existing one-weight-per-day rules unchanged), field returns to rest state showing the new value greyed.
- Empty field only before the first-ever weight exists.
- Card label renamed "Weight today" → "Weight" (field shows the last saved weight from any day; approved post-ship).
  *Intent: the field is the "current weight" — grey means saved, ink means unsaved input.*

## 4 — "Save to my foods" defaults to unchecked

**Change — LOCKED 2026-08-16**

- Claude confirm sheet and manual entry: the save-to-foods checkbox starts unchecked, always. Checking it is a per-item opt-in.
  *Intent: nothing enters the food library without an explicit choice.*

## 5 — Activities as negative entries (tiny v1)

**Change — LOCKED 2026-08-16**

- Activities log like any entry, via Claude or manual, with negative kcal ("Spin class −500"). No workout labeling beyond the name. No activity tab.
- Negative entry values render blue in the day log.
- Parser prompt: one added rule — exercise/activities return negative kcal, honoring the user's stated number.
- Hero drops the word "eaten": "1,100 of 1,547".
- Net-negative day (verified: only display code needs guards, the settlement math doesn't):
  - ring center percent clamps at 0 (never shows a negative %)
  - day bar draws a 2 px stub, not zero height — visible and tappable
- No Foods-tab exception: an activity saved to Foods is a food with negative kcal; all existing behavior (chips, editing) applies unchanged.
  *Intent: activities are ordinary entries with a sign, not a feature — the settlement math already treats a workout correctly (bigger surplus, faster repayment) with zero special cases.*
- Accepted quirk: hero may read "−500 of 1,547" after a morning workout before any food.
- Demo seed gains one activity entry so all negative-entry paths are testable pre-deploy.
